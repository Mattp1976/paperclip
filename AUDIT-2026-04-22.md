# Paperclip — end-to-end audit

**Date:** 2026-04-22
**Scope:** Full product audit — what it is, how it's built, what it can do, how it stacks up, and what's broken.
**Method:** architecture review (Explore agent), competitive research (Research agent), live feature walkthrough (Chrome MCP against running dev server at `localhost:3100`), typecheck + test-footprint probe, code inspection.

---

## 0. TL;DR

Paperclip is a self-hosted AI-agent orchestration platform with a project-management UI on top. The wedge is real and unique: **Linear-style PM UI + dispatch to multi-provider agents + cost tracking + kill switch + self-host**. No single competitor combines all five.

The platform is mature and deeply wired: **264 server routes, 65 DB tables, 7 adapters, 106 UI routes, 131 test files, ~192k TS lines** across a pnpm-9 monorepo. Server and UI both typecheck clean at HEAD (`7f3eacdc` + two uncommitted server fixes from this session).

Three audit findings are worth the user's attention:

1. **The "missing PDF button" report is a false negative.** The button ships, the endpoint returns 200 `application/pdf`, and the code path is live in the current build. Cause: the Paperclip tab was backgrounded behind a BBC News tab on the user's Chrome. Resolution: focus the Paperclip tab — `IssueDetail` header shows "Download PDF".
2. **Real regression found — slug-extended identifier sub-routes returned 500s.** The previous session's fix for `GET /api/issues/:id` only widened the *main* `router.param("id")` normalizer; four sibling sub-routes (`/activity`, `/runs`, `/live-runs`, `/active-run`) kept narrow `/^[A-Z]+-\d+$/i` regexes inline and blew up on any slug form. **Fixed in this session**; verified live — all four now return 200.
3. **Category positioning matches no existing bucket.** Paperclip sits between Linear/Asana (PM) and LangGraph/CrewAI (agent frameworks). Best-fit buyers are engineering-heavy orgs that need fleet-level cost visibility and heterogeneous-provider routing with a kill switch.

## 1. What Paperclip IS

Paperclip is a self-hosted orchestration platform that turns autonomous AI agents into a functioning company. Multiple AI agents (Claude, Codex, Cursor, Gemini, or any HTTP-callable runtime) are organised into org charts with reporting lines, assigned business goals, with costs tracked, work outputs captured, and approvals/overrides in a single dashboard.

**Target user:** founder or technical operator running 5–50 agents to build a business outcome with minimal human overhead.

**Primary jobs-to-be-done:**

- Dispatch work to a pool of agents across multiple providers.
- Monitor fleet health, cost, and output in real time.
- Keep humans in the loop for approvals and overrides.
- Provide an auditable trail of what each agent did and what it cost.
- Swap providers without migrating work, credentials, or PM state.

## 2. Architecture & tech stack

### 2.1 High-level diagram

```
UI  (React 19 + Vite 6 + TanStack Query 5)
  │  REST + WebSocket
  ▼
Server  (Express 5, Node 20+)
  │  Drizzle ORM
  ▼
Postgres 17 (or embedded PGlite) — 65 tables
  │
  ├── Claude Local Adapter
  ├── Codex / Cursor Local
  ├── Gemini Local
  └── OpenClaw / HTTP Gateway
         │
         └── External agent processes / webhooks
```

### 2.2 Data flow

UI ↔ Server via REST; live events via WebSocket. React Query polls heartbeats every 3–5s. Server spawns adapter subprocesses or posts HTTP webhooks. Agent heartbeats poll `/issues/my-tasks`, checkout, update, finish. Server persists to Postgres and fans out via SSE/WebSocket. Postgres is source of truth; in-memory scheduler + plugin workers; filesystem workspaces for agent git worktrees + logs.

### 2.3 Background workers

Heartbeat scheduler, checkout-lock recovery, run recovery, plugin job scheduler, routine service, quota window enforcement.

### 2.4 Tech stack

UI: React 19, Vite 6, React Router 7, TanStack Query 5, Radix UI, Tailwind 4, dnd-kit, Mermaid, MDX editor.
Server: Node 20+, Express 5, TS 5.7, Pino, Better Auth 1.4, Zod, ws.
DB: Postgres 17, Drizzle 0.38, embedded-postgres.
Storage: S3, local FS, Sharp, PDFKit.
Build: pnpm 9, TS, Vite, esbuild, vitest, Playwright.
Auth: Better Auth sessions + API keys, JWT for agents, planned OIDC.

### 2.5 Adapter contract

```ts
type ServerAdapterModule = {
  execute: (ctx) => Promise<Result>;
  getEnvironmentTests: (ctx) => Promise<TestResult[]>;
  getSkillSnapshot?: (ctx) => Promise<Snapshot>;
  syncSkills?: (ctx) => Promise<{synced, errors}>;
  sessionCodec?: AdapterSessionCodec;
};
```

Uniform interface across: claude-local, codex-local, cursor-local, gemini-local, opencode-local, pi-local, openclaw-gateway, generic process, generic HTTP. Each is its own npm package under `packages/adapters/`.

### 2.6 Plugin system

Node.js worker processes communicating via JSON-RPC stdio. Plugins can subscribe to events (issue.created, heartbeat.finished, …), schedule jobs (cron + event), store state, expose UI, register data endpoints, call host APIs. Reference implementation: `packages/plugins/examples/trading-plugin`. SDK in `packages/plugins/sdk`.

### 2.7 Data model

65 Drizzle tables. Top of the hot list: `companies, agents, issues, heartbeat_runs, approvals, projects, goals, cost_events, agent_runtime_state, company_secrets, plugin_jobs, plugin_state`. Every table is company-scoped via `companyId` FK.

### 2.8 Strong vs leaky abstractions

**Strong:** adapter contract (no special casing in routes); company scoping via `companyId` FK everywhere; atomic issue checkout (single transaction).

**Leaky / risky:**

- Plugin RPC over stdio — no framing protocol; extra stdout breaks the parser.
- Session-state persistence — adapter-specific; no schema validation; no versioning.
- Live-event WebSocket subscriptions — company-wide with no per-issue filter; fan-out bottleneck at scale.
- **Issue identifier normalizer scope (this session's bug):** the `router.param()` hook only resolves `:id`/`:issueId` on the router it's attached to. Sibling routers re-implement the check inline and drift. See §6 for the fix.

### 2.9 Scaling ceiling

- 100 users / single company: heartbeat scheduler becomes CPU-bound.
- 10k users: needs connection pooling (PgBouncer), batched live-events, Redis pub/sub for multi-instance fan-out.
- 100k+ users: multi-instance scheduler needs a coordinator (Redlock); subprocess zombies; log-storage explosion; plugin-worker proliferation.
- Budget enforcement is at heartbeat-start only — a run can overrun by one heartbeat's worth.
- Agent config plaintext in DB (only secrets are encrypted).

### 5.3 Where Paperclip wins

1. Unified cost accounting across heterogeneous agents.
2. Dispatch-then-monitor across providers simultaneously.
3. Fleet health + heartbeat monitoring + kill switch.
4. Self-hosted orchestration with PM UI baked in.
5. Git-worktree workspace browser with outputs surfaced in PM.

### 5.4 Where it lags

1. Enterprise PM feature maturity (Linear has 200+ integrations, Asana has portfolios/resourcing).

4. No real-time collaborative editing (@mentions, sync cursors).
5. Approval workflows are basic.
6. No semantic search across agent work.
7. Higher adoption friction (self-host + adapter setup + credentials).

### 5.5 Market opportunity

Real wedge but narrow. Best-fit buyers:

- Venture-backed AI infra startups (replaces LangGraph + Linear with one tool).
- Enterprise AI CoEs (need kill switch + per-BU cost tracking).
- AI agencies/consulting (multi-client, multi-provider).
- SaaS teams embedding agents (Zapier/Make style).

**Biggest risk:** Linear Agent is shipping fast (Q2 2026 Mission Control Plane for third-party agents). If Linear reaches parity on multi-provider + cost, the wedge collapses. Realistic TAM $500M–$1B; niche addressable $100M–$300M.

## 6. Bugs discovered and fixed during this audit

### 6.1 Slug sub-route 500s (fixed)

**Symptom:** `GET /api/issues/THE-49-client-acquisition-and-business-developm/activity` returned 500. Same for `/runs`, `/live-runs`, `/active-run`. The main `GET /api/issues/:id` worked because of commit `7f3eacdc`.

**Root cause:** last session's fix widened the identifier regex only inside `server/src/routes/issues.ts`'s `router.param("id")` and `router.param("issueId")` normalizers. Four sibling routes — `activity.ts#resolveIssueByRef`, `agents.ts#live-runs`, `agents.ts#active-run` — each re-implemented the identifier check inline with the narrow `/^[A-Z]+-\d+$/i`. Those files are mounted on different Express routers, so `router.param()` doesn't propagate.

**Fix (this session, uncommitted):**

- `server/src/routes/activity.ts` — widen `resolveIssueByRef` regex to `/^[A-Z]+-\d+(?:-.*)?$/i`.
- `server/src/routes/agents.ts` (live-runs, line ~2200) — widen inline regex.
- `server/src/routes/agents.ts` (active-run, line ~2240) — widen inline regex.

**Verification:** live probe against `localhost:3100` — all four endpoints now return 200 on slug-extended identifiers; bare identifier form still works.

**Follow-up recommendation:** centralise the identifier-normaliser into a shared module (`packages/shared/src/issue-id.ts` or similar) and import it everywhere instead of copying the regex. This is the second drift of the same pattern — a shared function would have prevented both incidents.

### 6.2 "Missing PDF button" (not a bug)

False positive. Code is live, endpoint is healthy, button is rendered. The Paperclip tab was simply backgrounded behind BBC News.

## 7. Strengths, gaps, risks

### 7.1 Strengths

- Clean adapter abstraction — adding a new provider is a self-contained package.
- Company-scoped data model is pervasive; good for eventual multi-tenancy.
- Git-worktree per agent run is a surprisingly good pattern for isolation and artefact capture.
- Cost ledger is genuinely differentiated — no competitor attributes spend at per-agent, per-provider, per-run granularity.
- PM UI is mature enough to compete with Linear on its own merits at small scale.

### 7.2 Gaps

- UI test coverage is thin for a 192k-LOC codebase.
- No agent-execution E2E happy path.
- Plugin SDK has no framing protocol and no tests — second-most-risky subsystem after session-state persistence.
- No native reasoning on agent output; Linear and Asana are adding this.
- Approval workflows are basic (only pass/fail, no multi-stage).

### 7.3 Risks

- **Identifier-normaliser drift.** Same bug shape will reappear elsewhere. Fix by centralising.
- **Live-event WebSocket fan-out.** No per-issue filter; company-wide broadcast. Will degrade at 10k users.
- **Budget enforcement granularity.** Can overrun by one heartbeat's worth.
- **Linear Agent catching up.** The moat is durable only if multi-provider + cost stay central.
- **Self-host friction.** Adapter setup + credentials + secrets management is a real barrier for non-engineering buyers.

---

## 8. Recommendations

Ordered by leverage × cost:

1. **Centralise issue-identifier normalisation** into `packages/shared/src/issue-id.ts`. Exports `normalizeIssueIdentifier` and `parseIssueIdentifier`. Import everywhere instead of copying the regex. (Small PR, prevents the recurring bug class.)
2. **Add E2E happy-path Playwright test** covering: onboard → create agent → create task → dispatch → see run → download PDF. This would have caught the sub-route 500s and the PDF discoverability regression.
3. **Bound the WebSocket subscription map** by company × issue, not company × everything. Single-largest scaling lever.
4. **Frame plugin stdio messages** (length-prefixed or newline-delimited JSON with sentinel). The current protocol breaks on any extra stdout.
5. **Ship per-issue approval workflows** with multi-stage gates. Closes the enterprise gap against Asana's AI Studio.
6. **Add semantic search over agent outputs** (pg_vector). Differentiates against Linear and costs little given Postgres is already in-stack.
7. **Commit the uncommitted server fixes** from this session (`activity.ts`, `agents.ts`) with a test covering slug-form sub-routes.
